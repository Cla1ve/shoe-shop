# Обоснование третьей нормальной формы

Предметная область: компания продаёт обувь. У каждой модели есть категория, производитель, описание, состав, цена и картинка. Модель продаётся в разных размерах, остатки считаются отдельно по каждому размеру. Клиенты оформляют заказы, в заказе несколько позиций (модель, размер, количество). Заказы могут оформлять клиенты, а смотреть и вносить вручную их могут менеджер и администратор.

## Сущности

| Таблица | Что хранит | Ключ |
|---|---|---|
| Roles | роли: Клиент, Менеджер, Администратор | id |
| Users | пользователи (логин, ФИО, роль) | id |
| Categories | категории обуви | id |
| Manufacturers | производители | id |
| Sizes | размеры | id |
| Products | модели обуви | id, уникально (name, manufacturer_id) |
| Stock | остатки модели в размере | (product_id, size_id) |
| Orders | заказы (дата, клиент) | id |
| OrderItems | позиции заказа | id |

Связи: категория и производитель к моделям один ко многим, модель и размер к остаткам один ко многим, роль к пользователям один ко многим, пользователь к заказам один ко многим, заказ к позициям один ко многим, модель и размер к позициям заказа один ко многим.

## Почему это 3НФ

**1НФ.** Все значения атомарные: размер, количество и цена лежат в отдельных столбцах, нет списков внутри ячеек. У каждой таблицы есть первичный ключ. Размеры не записаны через запятую в Products, а вынесены в Stock отдельными строками.

**2НФ.** В таблицах с составным ключом каждый неключевой столбец зависит от всего ключа. В Stock ключ (product_id, size_id), столбец quantity зависит от обоих: количество определено только парой «модель и размер». Остальные таблицы имеют ключ из одного столбца, там частичной зависимости быть не может.

**3НФ.** Нет зависимостей неключевых столбцов друг от друга (транзитивных).

- Название категории не хранится в Products, там только `category_id`, а название лежит в Categories. Иначе пришлось бы менять название в десятках строк.
- То же с производителем, размером и ролью пользователя.
- В Orders нет ФИО клиента: только `client_id`, ФИО хранится в Users. ФИО зависит от клиента, а не от заказа.
- В OrderItems нет названия модели, только `product_id`.

**Цена в OrderItems не нарушает 3НФ.** Столбец `unit_price` в позиции заказа не копия цены из Products, а отдельный факт: по какой цене продали на момент заказа. Если цена модели потом изменится, старые заказы должны остаться с прежней суммой. Поэтому цена хранится в позиции заказа.

**Ссылочная целостность.** Все внешние ключи объявлены с `ON UPDATE CASCADE`. При удалении заказа его позиции удаляются каскадом (`ON DELETE CASCADE`), при удалении модели удаляются её остатки. Нельзя удалить категорию, производителя, размер, роль или пользователя, на которых есть ссылки (`ON DELETE RESTRICT`), чтобы не потерять заказы.

## Ограничения

- `CHECK (price >= 0)`, `CHECK (quantity >= 0)` в остатках, `CHECK (quantity > 0)` в позициях заказа;
- `UNIQUE` на логин, названия справочников, размер, пару (название модели, производитель), номер заказа из файла.
